# 포스트 사실 검증

CLAUDE.md의 절대 규칙을 따른다. 특히 **커밋·푸시는 명시적 지시가 있을 때만** 한다.

글을 쓸 때는 몰랐던 오류가 게시 후에 드러난다. 이 블로그에서 실제로 그랬다. 스토크스 S₃ 식이
1절에서 정의한 위상차와 반대 순서로 적혀 있었는데(`089fbb9`), 계산 코드는 맞았기 때문에 수치
검증으로는 드러나지 않았고 게시 뒤에야 잡혔다. 이 스킬은 **한 편을 깊게** 본다. 시리즈를 한꺼번에
훑지 않는다. 글 하나에 들어 있는 사실 진술을 빠짐없이 장부에 올리고, 각각을 외부 근거로 확인한다.

이 스킬은 **공통 팩트체크 스킬 `fact-check`**(`~/.claude/skills/fact-check/SKILL.md`, 원본은
`repo_kms/skills/fact-check/`)를 프로필 `blog-post`로 쓴다. 원칙 1~4, 근거 등급, 검증자 프롬프트, 판정
어휘와 심각도, 장부 기록은 거기 있고, 여기에는 블로그에 묶인 것(한·영판, 그림, `_references/`, 커밋 관문)만
있다. 먼저 공통 스킬을 읽는다.

스크립트는 `S=.claude/skills/fact-check-post/scripts`, 공통 명령은 `K=../repo_kms/tools/factcheck.py`로 잡는다.

| 명령 | 하는 일 |
| --- | --- |
| `python3 $S/factcheck.py refs <글>` | 참고자료를 Crossref·DataCite·arXiv와 대조. 공통 명령 `$K refs`를 그대로 부른다 |
| `python3 $S/factcheck.py pair <한> <영>` | 한·영판의 수식과 숫자 차이 |
| `python3 $S/factcheck.py lint <글>` | 수식 속 `|`, `http://`, 없는 그림 파일, 닫히지 않은 `$$` |
| `python3 $S/factcheck.py claims <글>` | 주장 장부의 후보 줄 (식·연도·수치·인용·역사·캡션 태그) |
| `python3 $K add <주장.json>` | 3단계의 장부를 repo_kms 주장 장부에 넣는다 (`owner: me`, `source.id: post:<slug>`) |
| `python3 $K record <판정.json> --by fact-check-post/<모델>` | 5단계의 판정을 장부에 쓴다. 옛 판정은 `verdict_history`에 남는다 |

참조 파일은 공통 스킬에 있다. 필요할 때 읽는다.

- `~/.claude/skills/fact-check/references/claim-types.md` — 주장 유형별 검증법. 뒷부분이 블로그 글 유형과 이 블로그에서 실제로 나온 오류다 (3·4단계)
- `~/.claude/skills/fact-check/references/verifier-prompt.md` — 독립 검증 서브에이전트에게 줄 프롬프트 틀 (4단계)

## 원칙 1 — 고치는 범위를 좁게 묶는다

CLAUDE.md 절대 규칙 4는 기존 포스트를 고치지 말라고 한다. 이 스킬은 사용자가 사실 검증을
요청했을 때만 쓰는 예외이고, 범위는 다음과 같다.

- **고치는 것:** 사용자가 승인한 사실 오류. 필요하면 그 오류에 딸린 수식, 수치, 캡션, 그림과
  그림 생성 코드, 영문판의 같은 자리.
- **고치지 않는 것:** 어투와 문장 다듬기, front matter의 `date`와 파일명, 승인받지 않은 항목,
  같은 시리즈의 다른 편.

검증 중에 어색한 문장이 보여도 고치지 않고 보고서의 "범위 밖" 절에 적는다. 그건 `revise-post`의
일이다. 사실 수정과 어투 수정이 한 커밋에 섞이면 무엇을 왜 고쳤는지 이력에서 가려낼 수 없다.
다른 편에 영향이 가는 경우도 보고만 한다. S₃를 고쳤을 때 다른 편의 각주가 사실이 아니게 된
적이 있다(`bfbe282`). 그 편은 따로 승인을 받아 고친다.

## 원칙 2~4 — 공통 스킬과 같다

근거는 밖에서 가져오고(등급 A·B만 판정에, C는 단서, D(모델 기억)는 쓰지 않는다), 검증자는 초안을
보지 않으며(열린 질문만), "못 찾음"은 "틀림"이 아니다(틀림에는 반대 근거의 위치가 반드시 붙는다).
전문은 공통 스킬 `fact-check`의 원칙 2~4에 있다. 이 블로그에 묶인 것만 덧붙인다.

- 자료는 `_references/<slug>/` → `~/Library/CloudStorage/OneDrive-Personal/Documents/Research Library` →
  분야별 1차 자료(`repo_kms/config/sources.yaml`의 광학·계측) → 공개 DB 순서로 찾는다. 로컬을 건너뛰고
  "구할 수 없다"고 결론 낸 적이 두 번 있다. 공개 DB와 전문 확보 경로는 `research-sources` 스킬에 있다.
- 계산도 원칙 3을 따른다. 글의 숫자를 보지 않은 채 원리에서 다시 계산하고 마지막에 맞춰 본다.
- 이 블로그에서 가장 흔한 오탐은 규약 차이다. 부호, 회전 방향, 정규화 기준이 문헌과 다르면 오류가
  아니라 규약 차이일 수 있으니, 판정하기 전에 규약을 맞춰 본다.

## 0단계 — 대상 확인

검증할 한국어판을 정하고 딸린 것을 모은다.

```bash
slug=<slug>
ls _posts/*-$slug.md _posts/*-$slug-en.md _drafts/$slug*.md 2>/dev/null
ls _code/$slug/ _references/$slug/ 2>/dev/null
grep -oE '\]\(/posts/[a-z0-9-]+/\)' <글> | sort -u     # 이 글이 링크하는 앞 편들
```

영문판이 있으면 함께 검증하고 함께 고친다. 앞 편들은 기호와 규약을 대조하는 데만 쓴다(2단계).

## 1단계 — 기계 점검

사람이 볼 필요 없는 것부터 스크립트로 걸러낸다.

```bash
python3 $S/factcheck.py lint <글>
python3 $S/factcheck.py pair <한국어판> <영문판>
python3 $S/factcheck.py refs <글>
python3 .claude/skills/add-web-figures/scripts/figures.py check <한국어판> <영문판>
```

결과를 읽는 법:

- `refs`의 `!!`(MISMATCH, DEAD_DOI)는 거의 확실한 서지 오류다. 레코드와 표기를 나란히 보고 확정한다.
  `?`의 NOT_FOUND는 Crossref에 없다는 뜻일 뿐이다. 학회 논문이나 오래된 논문은 흔히 없다. 하지만
  지어낸 인용도 이렇게 나오므로 OpenAlex·arXiv·Research Library로 존재부터 확인한다. MANUAL(교재·
  학위논문·웹 자료)은 소장본 목차나 링크를 열어 판·연도·절 번호를 확인한다. `refs`가 확인하는 것은
  서지정보까지이고, 그 문헌이 본문 주장을 뒷받침하는지는 4단계에서 본다.
- `pair`가 보여주는 차이는 대부분 번역 때문에 생긴 정상적인 차이다(편 번호, "1930년대"와 "1930s").
  같은 수식이 한쪽에만 있거나 계산 결과가 다르면 한쪽이 틀린 것이다.

## 2단계 — 규약과 기호표

S₃ 오류는 수치 검증을 통과했다. 코드는 맞고 글 속 식 하나만 틀렸기 때문이다. 이런 오류는 정의와
사용을 대조해야 잡힌다. 글을 처음부터 읽으며 표를 만든다.

| 기호/규약 | 정의한 곳 (줄) | 정의 | 이후 쓰인 곳 | 정의와 맞나 |
| --- | --- | --- | --- | --- |
| Δ | L42 | φ_p − φ_s | L88 식, L120 코드 발췌 | L88 은 φ_s − φ_p 순서 ✗ |

- **규약 선언**을 먼저 찾는다. 시간 의존성(e^{±iωt}), 복소굴절률 부호(N = n ± ik), 위상차 순서,
  각도·회전 방향, 좌표 손방향, 정규화 기준, 광선 벡터(높이·각 또는 감소각) 같은 것들이다.
  글이 규약을 밝히지 않았으면 그것 자체를 보고한다.
- 글에서 쓰인 모든 기호가 정의되었는지, 정의한 뜻 그대로 쓰였는지 본다. 정의 없이 쓴 기호와
  같은 글자가 두 뜻으로 쓰인 곳(예: 파수 k와 소광계수 k)도 찾는다.
- 앞 편과도 대조한다. 시리즈가 이미 정한 규약이나 기호를 이 편이 뒤집지 않았는지 본다.
  앞 편 쪽을 고치는 것은 범위 밖이므로 보고만 한다.
- 문헌의 식을 가져온 곳은 그 문헌의 규약이 시리즈 규약과 같은지 본다. 다르면 변환이 되었는지 본다.

## 3단계 — 주장 장부

글의 사실 진술을 한 줄에 하나씩 장부에 올린다. 출판사 팩트체커들이 원고의 사실마다 밑줄을 긋고
출처를 대응시키는 방식이다. 빠뜨린 주장은 검증되지 않으므로, 이 단계의 목표는 빠짐없이 올리는
것이다.

```bash
python3 $S/factcheck.py claims <글>    # 후보 줄. 숫자 없는 주장은 놓치므로 본문 정독을 대신하지 않는다
```

본문, 별행 수식, 그림 캡션, 표, 코드 발췌, 각주를 절 단위로 읽으며 올린다. **영문판이 있으면 같은
문단을 나란히 놓고 읽는다.** 두 판의 뜻이 어긋나는 곳은 둘 중 하나가 틀린 곳이다. 한국어판의
"θ³ 이하의 항을 버린다"는 영문판의 "drops everything from θ³ on"과 나란히 놓으면 바로 드러난다.

숫자 없이 수학을 말로 하는 문장을 빠뜨리기 쉽다. "이하/이상", "커진다/작아진다", "앞/뒤",
"비례/반비례", "제곱으로 자란다", "~보다 가파르다" 같은 문장은 수식과 같은 무게로 장부에 올린다.
숫자를 엮는 문장("960 mm의 1.5%인 11 mm")은 그 산술도 주장이다.

장부의 열은 다음과 같다.

| # | 줄 | 유형 | 원문 (요약) | 문맥 없이 읽히는 주장 | 무게 | 근거 포인터 |
| --- | --- | --- | --- | --- | --- | --- |
| 7 | L98 | 수치 | 초점거리는 994.50 mm | 1편 렌즈(R1=…, t=100 mm, n=…)의 유효 초점거리는 994.50 mm | 핵심 | `_code/<slug>/abcd.py` |
| 12 | L71 | 역사 | 행렬 방법은 1930년대 초 T. 스미스가 처음 체계화 | 광선 행렬 방법을 처음 체계화한 사람은 T. Smith이고 시기는 1930년대 초다 | 곁가지 | [5] Hecht 6.2 |

- **문맥 없이 읽히게 고쳐 쓴다.** "이 값", "위 식", "1편의 렌즈" 같은 지시어를 실제 대상과 조건으로
  바꾼다. 그래야 검증자가 글 없이 판정할 수 있다(원칙 3).
- **유형**은 공통 `claim-types.md`의 블로그 글 유형을 쓴다. 장부의 `kind`로는 `수식` · `계산` · `상수·물성` ·
  `서지` · `역사·명명` · `그림·캡션` · `코드` · `일반화·인과` · `물리·원리` · `사실·서술` · `인용` · `수치·통계`다.
- **무게**는 핵심(논지가 기대는 주장)·보조·곁가지로 매긴다. 보고서 정렬과 심각도에 쓴다. 장부의
  `importance`로는 high·medium·low다.
- 일반화("항상", "유일한", "모든")와 인과("때문이다")도 주장이다. 인용한 문헌이 "관련이 있다"고
  했는데 글이 "원인이다"라고 썼다면 과장이다.
- 정의, 비유, 저자의 판단("이 편이 더 직관적이다")은 올리지 않는다.

장부가 다 차면 **repo_kms의 주장 장부에 넣는다.** 스크래치패드에 JSON(목록. 항목마다 `text`, `kind`,
`importance`, `locator`(줄 `L98/101`이나 `그림2`), `source: {"id": "post:<slug>", "url": "https://eddykim.github.io/posts/<slug>/",
"published": "<글 날짜>"}`, `domain: "광학·계측"`)을 쓰고 `python3 $K add <파일>`을 돌린다. 줄 ID는 문장과
`post:<slug>`에서 나오므로 같은 문장을 다시 넣어도 겹치지 않는다. 글을 고쳐 문장이 바뀌면 새 줄이 된다.

## 4단계 — 독립 검증

유형별로 검증 경로가 다르다. 자세한 방법은 `references/claim-types.md`를 읽는다.

**계산과 수식은 메인 세션이 직접 한다.**

1. `_code/<slug>/verify_*.py`가 있으면 다시 돌린다. 통과하지 않으면 그 자체가 발견이다.
2. `generate_figures.py`를 다시 돌리고 `git status`로 그림이 바이트 단위로 같은지 본다.
   달라졌으면 글이 게시된 뒤 코드나 환경이 바뀐 것이다. 캡션과 본문의 수치를 코드 출력과 대조한다.
3. 코드가 만들지 않은 수치, 그리고 코드 자체가 의심스러운 곳은 스크래치패드에 **독립 경로**로 새로
   계산한다. 글의 숫자는 보지 않은 채 원리에서 계산하고 마지막에 대조한다. 같은 식을 같은 방식으로
   다시 짜면 같은 실수를 반복하므로 다른 공식 체계를 쓴다(행렬 곱 ↔ 닫힌 식, 해석해 ↔ 수치 적분).
4. 수식마다 차원, 극한(두께→0, 무손실, 수직 입사, 근축), 보존(무손실이면 R+T=1), 대칭을 본다.
   특수한 값 하나에서만 확인하면 안 된다. Ψ=45°에서는 틀린 식과 맞는 식이 우연히 같았다.

**인용, 역사, 상수·물성은 서브에이전트에게 맡긴다.** 글을 쓴 맥락을 물려받지 않은 검증자가
필요하다(원칙 3). 유형별 방법은 공통 `claim-types.md`에 있다.

- 공통 `verifier-prompt.md`의 틀로 프롬프트를 만든다. 넘기는 것은 열린 질문, 근거 포인터
  (문헌명·로컬 경로·DOI), 근거 등급 규칙이다. **글 본문과 장부의 "원문" 열은 넘기지 않는다.**
- 문헌 묶음별로 하나씩, 한 에이전트에 질문 10개 안팎으로 묶는다. 보통 둘이나 셋이면 된다.
  검증자 하나가 15~20만 토큰을 쓰므로 이 단계가 비용의 대부분이다.
- **한 메시지에서 전부 띄우고 결과를 기다린다** (`run_in_background: false`). 같은 메시지의 호출은
  병렬로 돌고, 모두 끝나야 다음으로 넘어간다. 백그라운드로 띄우고 판정을 먼저 내리면 늦게 온
  답이 버려진다. 시험 실행에서 실제로 그래서 그림 캡션의 오류가 "확인 불가"로 묻혔다.
- 세션 전체의 서브에이전트 동시 실행 한도는 20이다. 여러 편을 병렬로 검사할 때는
  (동시에 도는 편 수) × (1 + 편당 검증자 수)가 20을 넘지 않게 묶는다. 편당 검증자 셋이면
  다섯 편이 한계다. 열 편을 한꺼번에 띄웠을 때 여섯 편의 검증자가 거절되어 원칙 3을 지키지 못했다.
- 검증자가 실패하거나 빈손으로 오면 그 질문만 다시 맡기거나 메인 세션이 직접 확인한다.
  그 뒤에도 근거가 없을 때만 확인 불가로 둔다.
- 돌아온 답을 장부와 대조하는 것은 메인 세션이 한다. 검증자의 답에 근거 위치가 없으면 그 답은
  확인 불가로 친다.

**웹 이미지 캡션은 메인 세션이 직접 본다.** 원 설명 페이지 하나만 읽으면 되므로 맡길 일이 아니다.
`python3 .claude/skills/add-web-figures/scripts/webimg.py info "<Commons 파일명>"`으로 원작자 설명을
가져와 캡션과 본문 서술(무엇을 어떻게 찍은 사진인지, 모델명, 파장)을 대조한다.

## 5단계 — 판정과 보고서

장부의 각 줄에 판정과 심각도를 단다. 판정 어휘는 공통 스킬(장부 스키마 v2)의 일곱 가지다.

| 판정 | 뜻 |
| --- | --- |
| 확인됨 | 등급 A·B 근거가 그대로 뒷받침한다 |
| 단서 필요 | 맞지만 조건이 빠졌다 (적용 범위, 규약, 근사) |
| 부분적·과장 | 일부만 맞거나 맥락이 빠졌다 (옛 보고서의 "부분적") |
| 틀림 | 근거가 반대를 말한다. 반대 근거 위치 필수 |
| 틀림 (시점) | 쓸 때는 맞았으나 그 뒤 바뀌었다 (제품·버전·표준 개정). 블로그에서는 드물다 |
| 규약 차이 | 문헌과 다르지만 글의 규약 안에서는 맞다. 규약을 밝혔는지는 따로 본다 |
| 확인 불가 | 근거를 못 찾았다. 시도한 경로를 적는다 |

판정은 보고서에만 적지 않고 **장부에 쓴다.** 스크래치패드에 판정 JSON(항목마다 `id`, `verdict`, `severity`,
`summary`, `evidence[{title, url, tier}]` — URL 없는 근거는 `url: null`에 `title`에 쪽·식 번호까지,
`reason`은 다시 판정할 때)을 쓰고 `python3 $K record <파일> --by fact-check-post/<모델>`을 돌린다.
`id`는 3단계 `add`가 출력한 값이다. 글을 고친 뒤 다시 검증하면 같은 명령이 옛 판정을 `verdict_history`에
남기고 덮는다.

| 심각도 | 기준 |
| --- | --- |
| 치명 | 독자가 따라 하면 틀린 결과가 나온다: 식의 부호·인자, 상수, 단위, 계산 결과, 반대 메시지를 주는 그림 |
| 중대 | 인용이 주장을 뒷받침하지 않음, 서지 오류, 역사·귀속 오류, 논지에 걸린 과장 |
| 경미 | 반올림, 표기 불일치, 곁가지 서술의 부정확 |

보고서는 `_references/<slug>/factcheck-YYYYMMDD.md`에 한국어로 저장한다. 이 폴더는 git에 올라가지 않는다.
고친 근거는 커밋 메시지에 남는다(9단계).

```markdown
# <제목> 사실 검증 (YYYY-MM-DD)

대상: _posts/<파일> (+ 영문판) / 장부 N건 (repo_kms claims.jsonl, post:<slug>) / 확인됨 a, 단서 b, 부분 c, 틀림 d, 시점 e, 규약 f, 불가 g

## 고칠 것 (심각도순)
### 1. [치명] L88 — S₃ 위상차 순서
- 현재: ...
- 근거: Born & Wolf 1.4.2절, 이 글 L42의 Δ 정의, `verify_x.py` 출력
- 수정안: ... (영문판 L91 같이)
- 영향: 그림2 다시 생성 / 같은 시리즈 3편 각주 (범위 밖, 따로 승인)

## 확인 불가 (시도한 경로)
## 규약 차이
## 범위 밖 (어투, 다른 편)
## 장부 전체
```

## 6단계 — 승인 (관문 1)

보고서의 **"고칠 것"만** 표로 보여준다(번호, 심각도, 줄, 현재 → 수정안, 근거 한 줄). 확인 불가와
규약 차이는 건수와 대표 사례만 보여준다. 장부 전체를 대화에 붙여넣지 않는다.

사용자가 항목별로 고른다. "전부"라고 하면 전부다. 확인 불가 항목에 대해 "표현을 누그러뜨리자"고
하면 단정 대신 출처를 밝히는 문장("헥트에 따르면 ~")으로 바꾸는 안을 낸다. 승인 전에는 아무 파일도
고치지 않는다.

## 7단계 — 최소 수정

- 승인받은 자리만 고친다. 오류가 있는 구절을 고치고, 그 문장의 나머지와 문체는 그대로 둔다.
- **한국어판과 영문판을 같이 고친다.** 영문판의 같은 자리는 `pair`로 찾는다.
- 그림이 바뀌어야 하면 `_code/<slug>/generate_figures.py`를 고쳐 다시 만들고, 바뀌어야 할 그림만
  바뀌었는지 `git status`로 확인한다. 웹 이미지(`ext-*`)는 손대지 않는다.
- 고친 결과가 장부의 다른 주장과 충돌하지 않는지 본다. 수치 하나를 고치면 그 값을 쓰는 다른 문장도
  바뀌어야 할 수 있다.

## 8단계 — 검증

```bash
python3 $S/factcheck.py lint <한국어판>; python3 $S/factcheck.py lint <영문판>
python3 $S/factcheck.py pair <한국어판> <영문판>
export PATH="$HOME/.rbenv/shims:$PATH"
JEKYLL_ENV=production bundle exec jekyll b -d _site --future
bundle exec htmlproofer _site --disable-external \
  --ignore-urls "/^http:\/\/127.0.0.1/,/^http:\/\/0.0.0.0/,/^http:\/\/localhost/"
rm -rf _site
```

`_drafts/`의 글이면 빌드는 생략하고 lint와 pair만 돌린다. 수식을 고쳤으면 `_site/posts/<slug>/`의
해당 자리가 표로 깨지지 않았는지도 본다.

## 9단계 — 보고와 커밋 (관문 2)

고친 항목, 바뀐 파일, 검증 결과를 보고한다. 커밋하기 전에 `git status`와 `git diff --stat`을 보여주고
확인을 받는다. 다른 세션이 스테이징한 파일이 딸려 들어가지 않게 경로를 지정해 커밋한다.

```bash
git commit -m "..." -- <고친 파일들>
```

커밋 메시지는 `fix(post): <slug> — <고친 내용 한 줄>`로 하고, 본문에 항목마다 **무엇이 틀렸고 어느
근거로 확인했는지**를 적는다. `089fbb9`의 메시지가 좋은 예다. 어느 쪽이 맞는지 1차 원리와 문헌으로
확인한 과정과, 그림 중 무엇이 바뀌고 무엇이 그대로인지를 남겼다.

게시된 글은 `date`와 파일명을 바꾸지 않으므로 `.claude/SCHEDULE.md`도 건드리지 않는다.
푸시는 사용자의 명시적 지시가 있을 때만 한다.

repo_kms의 장부(`ledgers/claims.jsonl`)는 이 저장소와 별개다. 그쪽은 작업 단위마다 커밋한다
(`cd ../repo_kms && git add ledgers/claims.jsonl && git commit -m "팩트체크: post:<slug> — N건"`). 승인 관문은
블로그 글을 고칠 때의 것이고 장부 기록에는 없다.
