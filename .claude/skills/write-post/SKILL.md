# 블로그 포스트 작성 워크플로우

CLAUDE.md의 절대 규칙과 저장 경로·스타일 규칙을 항상 준수한다.
분류 체계와 질문 세트는 레포 루트의 `categories.yaml`이 단일 출처(source of truth)다.
아래 단계를 순서대로 진행하며, **각 관문(승인 지점)을 건너뛰지 않는다.**

## 0단계 — 입력 수집

사용자로부터 받을 것:
- **주제** (필수)
- **참고자료** (선택): PDF 파일, URL, 코드 레포지토리 경로/링크

참고자료 처리:
- PDF → 읽고 핵심 내용 요약. 포스트에 첨부가 필요하면 `assets/files/posts/<slug>/`에 복사
- URL → 내용을 가져와 요약. 참고자료 섹션에 출처로 기록
- 코드 레포 → 구조와 핵심 코드를 파악. 포스트에 쓸 코드는 `_code/<slug>/`에 정리

주제가 너무 모호해 분류조차 안 될 정도면(1단계 진행 불가 수준), 초안 시작 전에 짧게 되묻는다.

## 1단계 — 분류 판단

`categories.yaml`의 `categories`를 읽고, 주제·참고자료의 키워드를 각 대분류의 `keywords`와
대조해 가장 잘 맞는 **대분류 + 소분류**를 판단한다.

- 명확히 하나로 맞으면 판단 결과를 사용자에게 한 줄로 알리고 넘어간다 (재확인 불필요).
- 두 개 이상의 대분류에 걸치거나 애매하면 AskUserQuestion으로 후보를 제시해 확인받는다.
- 어느 대분류의 키워드와도 잘 안 맞으면 **2단계(신규 분류 검토)**로 간다.

## 2단계 — 신규 분류 검토 (기존에 없는 주제일 때만)

`categories.yaml`의 `fallback.new_category_checklist`를 순서대로 확인한다:

1. 기존 대분류의 **소분류**로 편입할 수 있는가? → 가능하면 소분류로 추가하고 끝낸다.
2. 앞으로 최소 3편 이상 이어질 축인가? → 아니면 새 대분류를 만들지 않고 `fallback.questions`만 써서 이번 글은 무분류로 진행한다.
3. 질문 세트가 기존 대분류들과 실질적으로 다른가?

새 대분류를 만들기로 판단되면, `description`·`keywords`·`subcategories`(있다면)·`questions`를
초안으로 제시하고 **사용자 승인 후에만** `categories.yaml`의 `categories:` 아래에 추가한다.
승인 없이 `categories.yaml`을 수정하지 않는다.

## 3단계 — 질의응답

다음 순서로 사용자에게 묻는다. 답이 이미 대화 중에 나와 있으면 다시 묻지 않는다.

1. **공통 질문** (`categories.yaml`의 `common_questions`): 대상 독자, 분량, 핵심 메시지 한 줄,
   그림 필요 여부, 수식 포함 여부. `options`가 있는 항목은 AskUserQuestion으로, `type: free`
   항목(핵심 메시지 등)은 자유 서술로 받는다.
2. **분류별 질문** (1단계에서 정한 대분류의 `questions`): 주제와 실제로 관련 있는 것만 골라서
   묻는다 — 다섯 개를 기계적으로 다 던지지 않는다. 참고자료에서 이미 답이 나오는 항목은
   확인만 받고 넘어간다.

이 단계의 답변이 4~5단계(계획, 초안)의 내용을 결정한다.

## 4단계 — 이전 포스트 참고 여부 확인

계획을 세우기 전에 한 번 묻는다:

> "이전 포스트를 참고할까요? (문체 통일 / 관련 글 연결 / 참고 안 함)"

- **문체 통일**: `_posts/`에서 최근 포스트 2~3개를 읽고 어조·구성 패턴을 반영
- **관련 글 연결**: 주제와 관련된 기존 포스트를 grep으로 찾아 본문에 내부 링크 추가
- **참고 안 함**: CLAUDE.md의 스타일 규칙만 따름

## 5단계 — 글 계획 제시 및 승인 (관문 1)

1~4단계에서 모은 정보를 바탕으로 계획을 제시하고 **승인을 기다린다. 승인 전에는 초안을 쓰지 않는다.**

- 제목 후보 1~2개와 slug
- 목차 (소제목 단위, 각 섹션 한 줄 요약)
- 예상 분량 (3단계에서 정한 길이 기준)
- 필요한 자산 목록: 생성할 이미지/다이어그램, 저장할 코드, 첨부 파일
- front matter 초안 (1단계에서 정한 카테고리, 태그, `math: true` 여부)

사용자가 수정을 요청하면 계획을 고쳐 다시 승인받는다.

## 6단계 — 초안 작성

승인된 계획대로 작성한다:

1. `_posts/YYYY-MM-DD-<slug>.md` 생성 (CLAUDE.md front matter 템플릿 준수)
2. 자산 저장:
   - 이미지·다이어그램 → `assets/img/posts/<slug>/`
   - 전체 코드 → `_code/<slug>/` (그림 생성 스크립트는 `generate_figures.py`로 통일)
   - 첨부 파일 → `assets/files/posts/<slug>/`
3. 본문에서 자산은 루트 기준 경로로 링크 (`/assets/img/posts/<slug>/...`)
4. 작성 후 자체 점검: front matter 유효성, 링크 경로 실재 여부, 30줄 초과 코드 블록 여부

완료되면 사용자에게 초안 위치와 생성된 파일 목록을 알린다.

## 7단계 — 피드백 반복 (관문 2)

- 사용자의 피드백을 받아 수정한다. 횟수 제한 없음.
- 수정할 때마다 무엇을 바꿨는지 요약해서 보고한다.
- 사용자가 요청하지 않은 부분은 임의로 고치지 않는다.
- 로컬 미리보기를 원하면: `bash tools/run.sh` 안내 (직접 실행은 사용자 요청 시에만)

사용자가 "됐어", "이대로 좋아" 등 완료 신호를 주면 8단계로 넘어갈지 묻는다.

## 8단계 — 커밋·푸시 (관문 3)

**사용자의 명시적 지시가 있을 때만 진행한다.**

1. `git status`, `git diff --stat` 결과를 보여주고 커밋 대상 파일을 확인받는다
2. 이번 포스트 관련 파일만 개별 `git add` (CLAUDE.md 커밋 컨벤션 준수, `git add -A` 금지).
   2단계에서 `categories.yaml`을 수정했다면 그 파일도 함께 확인 후 add한다.
3. `post: <제목>` 형식으로 커밋 (categories.yaml만 바뀐 경우는 없음 — 항상 포스트와 함께 커밋)
4. 푸시 전 마지막 확인: "push하면 블로그에 공개됩니다. 진행할까요?"
5. `git push` 후 배포 확인 방법 안내 (Actions 탭 또는 사이트 URL)

## 예외 처리

- 참고자료를 읽을 수 없으면(접근 불가 URL, 손상된 PDF) 그 사실을 알리고 나머지로 진행할지 묻는다
- 같은 날짜·slug의 포스트가 이미 있으면 덮어쓰지 말고 사용자에게 알린다
- 워크플로우 중간에 사용자가 다른 작업을 시키면, 돌아왔을 때 현재 단계를 상기시킨다
