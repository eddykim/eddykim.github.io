# 포스트 교정 및 이중언어 작업

CLAUDE.md의 절대 규칙을 따른다. 특히 **커밋·푸시는 명시적 지시가 있을 때만** 한다.
분류와 영문 대응명은 `categories.yaml`이 단일 출처다.

## 0단계 — 대상 확인

교정 대상 파일을 찾는다. 재발행 작업이면 `_drafts/`에, 이미 게시된 글의 수정이면
`_posts/`에 있다.

**재발행은 원래 발행 순서를 지킨다.** 글 사이의 링크가 전부 과거 글을 향하므로,
순서대로 올리면 매 시점에 링크가 유효하다. 순서를 어기면 앞 글로 가는 링크가 404가 되고
htmlproofer가 실패해 **배포 전체가 막힌다.** 순서는 각 파일 front matter의 원래 `date`로
판단한다.

## 1단계 — 사실 오류 점검 (어투보다 먼저)

문장을 다듬기 전에 내용이 틀린 곳을 찾는다. 어투만 고치고 오류를 남기면 더 나쁘다.

확인할 것:

- **수식 표기.** 실제로 `$n = n - ik$`처럼 좌우변에 같은 기호가 들어가 성립하지 않는 식이
  있었다. 복소굴절률은 `$N = n - ik$`가 맞다.
- **시리즈 간 표기 일관성.** 같은 물리량을 다른 편에서 다른 기호로 쓰고 있지 않은지
  본다. 앞 편을 열어 대조한다.
- **중복 서술.** 같은 내용을 두 문장이 반복하는 곳. 그림 설명에서 자주 나온다.
- **`http://` 링크.** htmlproofer가 실패 처리해 배포를 막는다. `grep -rn "](http://" _posts/ _drafts/`
  로 훑고, `curl -sI https://...`로 HTTPS 응답을 확인한 뒤 스킴을 바꾼다.
  자세한 내용은 CLAUDE.md와 배포 관련 메모를 참고한다.

찾은 오류는 교정 작업과 **구분해서** 사용자에게 보고한다. 어투 수정은 취향이지만
오류 수정은 아니기 때문이다.

## 2단계 — 어투 교정 (논문체)

목표는 **한국어 논문체**다. 평서문 종결(`~이다`)은 이미 이 블로그의 기본이므로,
바꾸는 것은 종결어미가 아니라 **문어체 여부**다.

### 바꾸는 것

| 유형 | 전 | 후 |
| --- | --- | --- |
| 구어체 축약 | 이때 쓰는 **게** 반복법이다 | 이때 사용하는 **것이** 반복법이다 |
| 구어체 축약 | 그래서 필요한 **게** ~다 | 여기서 ~가 **필요해진다** |
| 비유적 동사 | 행렬을 한 번 **뒤집어** 풀린다 | **행렬의 역을 구해** 풀린다 |
| 평가어 | 빨간 선은 **딴판이다** | **반면** 빨간 선은 |
| 평가어 | 그대로 **눌러앉는다** | 그 **값을 유지한다** |
| 평가어 | **별생각 없이** 크게 잡았다 | **충분히 크게 잡아** |
| 1인칭 | **내가 오래 다뤄온** 예시로는 | **대표적인 예가** |
| 구어체 명사 | 안 맞는 **정도** | **불일치** |
| 결론 문장 | 완전히 다른 결과가 나온 것이다 | 수렴과 발산을 **가른 것이다** |

점검용 grep:

```bash
grep -nE "하는 게|필요한 게|찾는 게|쓰는 게|되는 게|이건 |이게 |딴판|눌러앉|굴러간|별생각|안 맞는 정도" <파일>
grep -nE "내가 |제가 |나는 " <파일>   # "하나는", "지나가는" 같은 부분 문자열 오탐에 주의
```

### 유지하는 것

- **수사적 질문.** "잔차를 제곱하여 합하는 이유는 무엇인가" 같은 문장. 논문에서도 쓰이고,
  답을 주기 전에 질문을 던지는 구조는 이 블로그 글의 강점이다. 없애면 손해다.
- **평서문 `~이다`.** 이미 맞다.
- **영문 병기.** `후초점면(back focal plane, BFP)` 형식을 유지한다.

### 하지 말 것

원문의 목소리를 지우지 않는다. **과거에 소개글을 과하게 다듬었다가 전부 되돌린 적이 있다.**
`마구잡이로`, `날 도와줄 LLM이 있다면` 같은 표현이 오히려 저자의 목소리인데 매끄럽게
정리해버린 것이 문제였다.

- 문법이 실제로 깨진 곳과 구어체를 고치되, **멀쩡한 문장을 더 좋게 만들려 하지 않는다.**
- 문장을 길게 이어 붙이지 않는다. `~인데, ~해서, ~하니`로 세 절을 한 문장에 넣으면
  보고서처럼 읽힌다. 논문체는 격식이지 만연체가 아니다.
- **굵은 글씨로 항목 라벨을 다는 구성을 쓰지 않는다.** 전형적인 AI 글 문법이다.

## 3단계 — 한국어판 승인 (관문 1)

교정한 내용을 **대표 사례 표(전/후)** 로 정리해 보여주고 확인을 받는다. 전체 본문을
다시 붙여넣지 않는다. 함께 보고할 것:

- 1단계에서 찾은 사실 오류와 그 수정
- 어투 교정의 원칙 (무엇을 바꾸고 무엇을 남겼는지)
- 본문 글자수

승인 전에는 영문판 작업으로 넘어가지 않는다. 한국어판이 확정돼야 그것을 옮길 수 있다.
**확정 전에 번역하면 곧 고칠 문장을 번역하는 셈이라 작업이 두 번 된다.**

## 4단계 — 그림 영문화

그림에 한글 라벨이 있으면 영문판에 그대로 쓸 수 없다. `_code/<slug>/`의 생성
스크립트를 언어별 라벨 사전 구조로 고쳐 다시 만든다.

```python
LABELS = {
    "ko": {"dir": BASE_DIR,                      "font": KFONT, "legend": LFONT,
           "xlabel": "두께 d (nm)", ...},
    "en": {"dir": os.path.join(BASE_DIR, "en"),  "font": {},    "legend": {},
           "xlabel": "Thickness d (nm)", ...},
}
```

- 데이터 계산은 **한 번만** 하고 라벨만 갈아 끼운다. `render(labels)` 함수로 분리한다.
- 영문 그림은 `assets/img/posts/<slug>/en/`에 같은 파일명으로 저장한다.
- 한글 폰트(`AppleGothic`)는 한국어판에만 지정한다. 전역 폰트를 바꾸면 로그축 눈금의
  마이너스 기호가 깨진다.
- 실행 후 **한국어 그림 파일이 변하지 않았는지 `git status`로 확인한다.** 같은 seed를
  쓰므로 바이트 단위로 동일해야 한다. 변했다면 데이터 생성 코드를 건드린 것이다.

## 5단계 — 영문판 작성

**번역이 아니라 영어로 다시 쓴다.** 한국어 문장을 그대로 옮기면 영어 번역체가 된다.
논문체 영어의 기본을 따른다 — 능동태를 우선하되 방법 서술에는 수동태를 쓰고,
문장을 짧게 끊는다.

front matter 규칙 (CLAUDE.md의 영문판 절과 동일):

```yaml
---
title: "..."
lang: en
lang-exclusive: ["en"]              # 빠뜨리면 기본값 ko 가 남아 /en/ 에서 사라진다
permalink: /posts/<slug>/           # 파일명의 -en 접미사가 URL 에 새지 않게 고정
page_id: <slug>                     # 한국어판과 짝을 맺어 hreflang 이 붙는다
date: <한국어판과 동일>
categories: [<en_names 대응>]        # categories.yaml 의 en_names 를 따른다
---
```

**한국어 원문에도 같은 `page_id: <slug>` 한 줄을 추가한다.** 없으면 두 글이 서로의
번역본으로 인식되지 않아 hreflang이 붙지 않고, 검색엔진이 중복 콘텐츠로 보아 서로
순위를 깎는다.

파일명은 `_posts/YYYY-MM-DD-<slug>-en.md`이고, 이미지 경로는 `.../en/`을 가리킨다.

## 6단계 — 로컬 검증

푸시 전에 반드시 돌린다. 배포가 사흘간 멈췄던 사고는 이 검증이 없어서 생겼다.

```bash
export PATH="$HOME/.rbenv/shims:$PATH"
JEKYLL_ENV=production bundle exec jekyll b -d _site --future
bundle exec htmlproofer _site --disable-external \
  --ignore-urls "/^http:\/\/127.0.0.1/,/^http:\/\/0.0.0.0/,/^http:\/\/localhost/"
```

`--future`를 붙여야 예약 날짜 글까지 빌드되어 검증된다. 확인할 것:

- `_site/posts/<slug>/`와 `_site/en/posts/<slug>/`가 **둘 다** 생겼는가
- hreflang이 서로를 가리키는가
  (`grep -oE '<link rel="alternate"[^>]*>' _site/posts/<slug>/index.html`)
- 영문 카테고리 경로가 영문인가 (`/en/categories/optimization/`)
- htmlproofer가 통과하는가

검증이 끝나면 `rm -rf _site`로 지운다.

## 7단계 — 발행일과 푸시 (관문 2)

발행일은 **다음 월·수·금 20:00 KST**로 잡는다. 파일명의 날짜와 front matter의 `date`를
맞춘다. 푸시해두면 워크플로의 cron이 그 시각에 자동으로 올린다. 즉시 올려야 하면
Actions 탭에서 `Build and Deploy`를 수동 실행한다.

커밋 메시지는 `post: <제목> 개고 + 영문판` 형식으로 하고, **왜 그렇게 고쳤는지**를 본문에
남긴다. 특히 사실 오류 수정은 근거를 적는다.

푸시는 사용자의 명시적 지시가 있을 때만 한다.

## 특수 사례 — 끊어둔 링크 복원

전체 포스트를 내릴 때 최적화 2편·4편이 1편을 링크하고 있어 htmlproofer가 실패했다.
임시로 링크를 일반 텍스트로 바꿔둔 상태다. **2편과 4편을 재발행할 때 복원해야 한다.**

```markdown
1편  →  [1편](/posts/optimization-gradient-descent/)
```

1편이 이미 발행돼 있어야 유효하다. 순서를 지키면 자연히 충족된다.
